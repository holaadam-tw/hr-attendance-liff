## Context

同時請假檢查目前完全在前端執行：`checkLeaveAvailability()` 讀取公司設定及重疊的待審／已核准申請，若新申請會使人數超過 `max_concurrent_leave`，便回傳 `ok: false`；`records.html` 會停用送出按鈕，`submitLeave()` 也會再次中止。資料庫的 `submit_leave_request` RPC 本身沒有同時請假硬限制，因此可在不改 schema 或 RPC 的情況下調整成建議性警告。

## Goals / Non-Goals

**Goals:**

- 超過公司設定門檻時仍允許員工送出待審請假。
- 在日期選擇、送出結果及管理端設定畫面清楚表達人力風險。
- 保留現有多租戶篩選、重疊日期計算、RPC 寫入及設定資料。
- 以自動化測試鎖定「警告但不阻擋」及文案語意。

**Non-Goals:**

- 不自動核准超額申請，也不改變主管核准／駁回流程。
- 不新增資料表、欄位、RPC、排程或 LINE 通知。
- 不改變假別、可請日期、時數假起訖或假期額度規則。

## Decisions

1. **沿用 `max_concurrent_leave` 設定鍵，改變其產品語意。** 既有各公司數值直接成為警告門檻，可避免 migration 與雙設定相容問題。替代方案是新增設定鍵，但會造成舊值搬移與兩套設定並存。
2. **保留 `checkLeaveAvailability()` 作為唯一計算來源。** 回傳新增 `thresholdExceeded`，同時請假超過門檻時 `ok` 仍為 `true`；呼叫端依旗標顯示醒目警告，但不得停用送出。這可避免日期提示與實際送出採用不同算法。
3. **超過門檻的判定沿用現行公式。** 只有「既有重疊人數 + 本次申請人」大於設定值才警告；等於門檻時不視為超額。例如門檻 2 人，已有 2 人時第 3 人會收到警告。
4. **資料寫入不變。** 仍只呼叫既有 `submit_leave_request` RPC，申請狀態維持待審，最終人力決策由主管處理。
5. **管理端改名為警告門檻。** 保留 1–10 人調整範圍，但移除「自動駁回」敘述，避免管理者誤解。

## Risks / Trade-offs

- [主管可能核准過多人同時休假] → 前端在超額日期及管理月曆顯示醒目警告，將決策與責任留在主管審核。
- [舊設定名稱仍是 `max_concurrent_leave`] → 程式與文件明確註記為相容性鍵，使用者介面只顯示「警告門檻」。
- [日期檢查查詢失敗時無法預警] → 沿用既有 fail-open 行為，避免網路短暫失敗阻止依法提出請假；實際申請仍受 RPC 驗證及主管審核。
- [前端快取導致新舊語意混用] → 更新 `common.js` 與 `modules/leave.js` 的資源版本並以回歸測試檢查。

## Migration Plan

1. 先在 `dev` 更新規格、前端與測試。
2. 通過專項、完整、QA、RLS／多租戶及 OpenSpec strict 驗證。
3. 後續由使用者另行授權才可合併 `main`；本次不部署、不改資料庫。
4. 回復時還原本次前端與文件變更即可，無資料回復需求。

## Open Questions

無；使用者已確認超過門檻仍可送出並交由主管審核。
