## Context

`checkin.html` 已有 LIFF 初始化、員工身分、相機串流、照片 JPEG 編碼、GPS 暖機與打卡階段診斷，但這些資訊分散在主流程中，員工只能在真正打卡失敗後看到部分結果。既有 `checkin-debug.html` 雖有診斷畫面，卻包含會實際呼叫 `quick_check_in` 的寫入按鈕，不適合提供給一般員工。

相機與 GPS 問題多半發生在特定手機及 LINE WebView，管理者從自己的電腦做系統檢查無法重現。因此採兩層驗證：CI／離線測試檢查程式規則，員工手機上的安全檢查確認當下裝置環境。

## Goals / Non-Goals

**Goals:**

- 在正式打卡前，用同一支手機確認 LIFF 身分、網路、相機有效畫面、JPEG 編碼與 GPS。
- 將錯誤轉成員工看得懂、可立即操作的處理方式。
- 產生可截圖回報、但不洩漏照片、精確座標與個人識別碼的結果。
- 重用正式打卡 helper，讓自我檢查能抓到與真實流程相同的相機／照片問題。
- 保證檢查本身不寫入考勤、不送 RPC、不上傳照片，且不破壞原本相機串流。

**Non-Goals:**

- 不從管理者電腦遠端檢測員工手機硬體或權限。
- 不改變 GPS 範圍、精度、下班時限、班別或任何打卡業務規則。
- 不以測試上傳或測試打卡驗證 Supabase Storage／`quick_check_in`，避免產生正式資料。
- 不新增資料庫健康檢查表、RPC、migration 或自動收集員工裝置資訊。
- 不把自我檢查結果設為打卡的強制門檻；即使部分檢查失敗，員工仍可依現行規則嘗試打卡。

## Decisions

### 1. 入口放在正式打卡頁，而不是另建管理頁

在主打卡按鈕下方加入次要按鈕「🩺 打卡環境檢查」。檢查必須在發生問題的同一支手機與同一個 LINE WebView 執行，才能看見真實權限、相機串流與 GPS 狀態。

替代方案是強化 `checkin-debug.html`；不採用，因該頁含正式打卡 RPC 測試，誤觸會寫入考勤，而且與主流程 helper 容易分歧。

### 2. 使用結構化、可逐項逾時的檢查器

新增 `runCheckinHealthCheck()` 統籌固定項目，每項回傳 `status`、`code`、`elapsedMs`、`message` 與 `action`。各檢查獨立逾時，單項失敗不阻止後續項目，最終狀態只分為「全部正常」或「有項目需處理」。

### 3. 相機檢查重用正式 helper，但只在記憶體處理照片

串流模式呼叫 `ensureCameraReadyForCapture()` 確認有效 frame，再畫入暫存 canvas 並呼叫 `canvasToJpegBlob()`。成功後只記錄 Blob 大小區間，立即丟棄參照，不建立 Object URL、不上傳、不保存。

若裝置只能使用 `input[capture]` 系統相機，結果顯示「需手動測試拍照」並提供獨立的測試拍照入口；測試檔同樣只做記憶體 JPEG 編碼後清除 input，不呼叫 `handleCapturePhoto()`。

### 4. GPS 檢查使用正式定位路徑，但回報不含精確座標

呼叫與打卡相同的 GPS helper，回報是否取得、耗時及精度等級。畫面只顯示「已取得／太慢／權限被拒／抓不到」與必要的權限操作，不顯示緯經度；診斷摘要也不包含座標。

### 5. 網路檢查只做無寫入請求

以 `fetch` 對目前站台的 `checkin.html` 發送 `cache: 'no-store'` 的 GET 並設短逾時，確認 LINE WebView 可連到正式靜態站。後端可用性則以頁面已完成的 LIFF 與員工身分初始化作為訊號；不新增測試上傳或測試 RPC。

### 6. 結果採白話建議及隱私安全摘要

每種錯誤碼對應固定建議，例如開啟 LINE 相機／定位與精確位置、移到窗邊、關閉重開 LINE。摘要只包含檢查時間、粗略平台、頁面版本、各項狀態／錯誤碼／耗時，不含姓名、ID、User-Agent 原文、照片或座標。

### 7. 檢查與正式打卡互斥

檢查期間暫時停用正式打卡與重複檢查按鈕；結束後恢復原狀。檢查不停止可用串流；若因檢查而重開相機，結束時保留它供正式打卡使用。離開頁面仍沿用既有 `stopCamera()` 清理。

### 8. 定位自我檢查採全新短時探測，不沿用正式打卡多階段等待

Android／LINE 實機顯示：手機定位關閉時，原本重用 `resolveGpsLocation()` 會依序等待共用 GPS manager、高精度 watch 與兩段 fallback，累積約 30 秒才失敗。自我檢查改用專用 `getHealthGpsLocation()`：先以最多 0.5 秒讀權限狀態，再直接要求一筆不使用快取的高精度位置，硬性最多等待 7 秒。探測只在記憶體回傳當次結果，不更新 `cachedLocation`、`localStorage` 或既有精確座標診斷。正式打卡仍使用原本完整流程與精度規則，不受影響。

### 9. 問題結果使用高對比視覺層級

只要有失敗項目，總結改為深紅底白字「目前可能無法打卡」，外框加粗紅色；各失敗項目使用淡紅底、粗紅框及「需要立即處理」，操作步驟獨立放在黃色提示框。正常項目維持綠色，尚未完成項目使用黃色，使員工可從截圖一眼找到問題。

## Risks / Trade-offs

- [靜態站 GET 正常不代表 Supabase Storage／RPC 一定正常] → 結果明確標示「未建立測試資料」，正式後端寫入仍由既有打卡錯誤階段診斷負責。
- [iOS／LINE 不一定支援 Permissions API] → 權限查詢未知時直接做實際相機／定位檢查，不把「無法查權限」當成失敗。
- [短時 GPS 檢查可能把冷啟動或室內弱訊號判為需處理] → 文案不武斷宣稱定位一定關閉，而是明確寫「最常見原因」並列出定位服務、LINE 權限與重新檢查步驟；正式打卡仍保留完整定位等待。
- [系統相機 fallback 無法全自動拍照] → 提供明確的第二步「拍一張測試照」，並保證照片不保存、不上傳。
- [自我檢查會短暫使用相機與定位] → 按鈕文字與說明先告知用途，且只在員工主動點擊後執行。

## Migration Plan

1. 在 `dev` 實作打卡頁入口、檢查器及測試拍照安全路徑。
2. 新增離線回歸測試，執行 QA、完整 `npm test`、hook 與 RLS 最終審查。
3. 由使用者依既有 Git 流程手動提交至 `dev`；經實機驗收後再手動合併 `main`。
4. 回滾時只需還原本次前端、測試與文件 commit；沒有 DB 或 schema 回滾步驟。
